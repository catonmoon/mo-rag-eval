# MO Rag Evaluation — инструкция по работе

Для тех, кто оценивает RAG-систему МОРАГ, ведёт эталоны и разбирает вердикты.
Развёртывание — в [DEPLOY.md](DEPLOY.md), устройство кода — в [README.md](README.md).

## Коротко: что делает система

1. Вы загружаете файл с ответами вашей RAG-системы на вопросы из набора.
2. LLM-судья сравнивает каждый ответ с **эталоном** (gold) и ставит 1 (верно) или 0 (неверно).
3. Результат появляется строкой в **лидерборде**, а по каждому вопросу видно ответ, эталон и вердикт.
4. Человек может **поправить эталон**, если ошибка в нём, или **переопределить вердикт**, если ошибся судья.

## 1. Вход

Открыть сайт, ввести пароль. Пароль задаёт администратор (`EDIT_PASSWORDS`).
Все действия, включая правку эталонов, доступны любому, кто знает пароль.

## 2. Подготовить ответы

1. В блоке **📥 Downloads** скачать вопросы — JSONL вида `{"id": "1", "question": "..."}`.
2. Прогнать вопросы через RAG-систему.
3. Собрать файл ответов — **одна JSON-строка на вопрос**:

```json
{"id": "1", "answer": "Текст ответа", "sources": ["https://confluence/...pageId=123"]}
{"id": "2", "answer": "Текст ответа", "sources": []}
```

- `id` — строкой, как в файле вопросов.
- `sources` — необязательно: список ссылок, откуда RAG взяла ответ (или объекты `{"file": "doc.pdf", "page": 12}`).
  Нужен для метрики **LinksOK** — совпали ли ссылки с источником в эталоне.
- Можно отвечать не на все вопросы: точность считается по тем, на которые есть ответ.
- Имя файла становится названием строки в лидерборде — называйте осмысленно
  (`morag_v2_208q_2026-10-28.jsonl`).

## 3. Отправить на оценку

Блок **📤 Submit your answers**:

1. **Gold version** — против какой версии эталона судить. Обычно `active` (текущая).
   Архивная версия нужна, чтобы честно сравнить с прошлым прогоном.
2. **Secondary judge** — включить второго судью (MiniMax `minimax-m3.1-flash`). Тогда:
   - оба согласны → верно / неверно;
   - разошлись → 🟡 **ToCheck** (спорный вопрос, проверит человек).

   Без галки работает один судья и ToCheck почти не бывает.
3. Загрузить файл → **Submit**.
4. Оценка идёт в фоне, виден прогресс-бар. 200 вопросов — несколько минут.
   Когда закончится, нажать **🔄 Refresh** у лидерборда.

Повторная отправка тех же ответов проходит мгновенно: вердикты берутся из кэша.

## 4. Читать лидерборд

| Колонка | Что значит |
|---|---|
| `filename` | имя загруженного файла (`_HumChg` — версия с ручными правками, см. п. 7) |
| `Correct` / `Wrong` / `ToCheck` | число верных, неверных и спорных ответов |
| **`accuracy`** | **Correct / (n_submit − ToCheck)** — спорные не считаются ни в плюс, ни в минус |
| `LinksOK` | в скольких ответах ссылки совпали с источником эталона |
| `n_submit` | сколько непустых ответов было в файле |
| `n_valid` | n_submit − ToCheck — знаменатель accuracy |
| `total` | сколько вопросов в эталоне |
| `gold_version` | против какой версии эталона судили |
| `#HumanChg` | сколько вердиктов человек переопределил в этом прогоне |

Сравнивать прогоны корректно только при **одной и той же `gold_version`** и одном режиме судейства
(с галкой Secondary или без).

## 5. Разбирать ответы по вопросам

Блок **🔍 Evaluation details**: выбрать прогон в **Select submission**. Ниже — карточка на каждый вопрос:

- вопрос, **ответ RAG**, **эталон**, источники RAG и источник эталона рядом;
- цвет: 🟢 верно, 🔴 неверно, 🟡 спорно.

Сверху счётчик по прогону: answered / 🟢 / 🔴 / 🟡.

Типовой разбор красной карточки:

| Что видно | Что делать |
|---|---|
| RAG ответил неверно или неполно | ничего — это реальная ошибка RAG |
| RAG ответил верно, судья придрался | переопределить вердикт → п. 7 |
| Ошибка или устаревшие данные **в эталоне** | поправить эталон → п. 6 |
| Вопрос некорректный / без ответа в документах | поправить вопрос или эталон → п. 6 |

## 6. Править эталоны

Эталон — это вопрос + правильный ответ + источник. Правится прямо в карточке вопроса.

1. На карточке нажать **✏️ Edit** — под ней откроется форма:
   - **Question** — текст вопроса;
   - **Gold answer** — эталонный ответ. Пишите **ключевые факты**, которые обязан содержать ответ:
     судья считает верным ответ, где есть все они (лишние подробности не штрафуются);
   - **Источник** — раздел и ссылка на документ (`Источник: https://...`). Нужен для LinksOK.
2. **💾 Save** — правка сохранена и сразу действует на новые оценки против `active`.
   **↩ Reload from active** — отменить несохранённое в форме. **✖ Close** — закрыть.
3. После первой правки эталон переходит в режим **🔓 Draft** (вверху блока). Можно править дальше —
   сколько угодно вопросов.
4. Когда серия правок закончена — **💾 Save New Gold Set**. Это фиксирует версию:
   - предыдущий вариант уходит в архив с датой;
   - рядом сохраняется **diff** — что именно поменялось;
   - статус возвращается в **🔒 Fixed**.
5. Блок **📚 Gold versions** — список версий; **📜 Show diff** показывает изменения выбранной.

Важно:

- Правка эталона **не пересчитывает старые прогоны**. Чтобы увидеть эффект — отправить те же ответы
  ещё раз против `active`: неизменённые вопросы возьмутся из кэша, перепроверятся только правленые.
- Добавлять и удалять вопросы через интерфейс нельзя — только править существующие
  (новые вопросы — через администратора, в файле `data/gold/answers_gold.jsonl`).
- Файл вопросов в **Downloads** обновляется после перезапуска сервиса.

## 7. Переопределять вердикты судьи (human override)

Когда судья ошибся, а эталон в порядке:

1. В **Select submission** выбрать прогон.
2. На карточке нажать 🟢 (верно), 🔴 (неверно) или 🟡 (спорно). Повторное нажатие той же кнопки снимает отметку.
   Отметки сохраняются сразу и видны в колонке `#HumanChg`.
3. Разметив всё нужное — **📨 Submit Human Overrides**. В лидерборде появится новая строка
   `<имя>_HumChg` с пересчитанной accuracy. Исходная строка (чистый судья) остаётся — видно,
   насколько судья ошибался.

Отметки привязаны к конкретному прогону. Если ответы прогнали заново — размечать заново.

## 8. Типовые сценарии

**Оценить новую версию RAG.** Скачать вопросы → прогнать → загрузить против `active`
(с Secondary, если нужна надёжность) → Refresh → сравнить с прошлым прогоном той же `gold_version`.

**Разобрать прогон.** Открыть детали → пройти 🔴 и 🟡 → каждое: ошибка RAG / ошибка судьи (override) /
ошибка эталона (Edit) → Save New Gold Set → Submit Human Overrides → при правке эталона перезалить ответы.

**Сравнить с прошлым честно.** Перезалить старый файл ответов против новой `active` — получите
обе модели на одном эталоне.

## 9. Если что-то не так

| Симптом | Причина / что делать |
|---|---|
| Прогресс-бар завис, строки нет | Нажать Refresh через пару минут; если пусто — администратору: логи сервиса, вероятно ошибка ключа или модели судьи |
| Много 🟡 при выключенном Secondary | Судья не ответил (сбой API) — перезалить файл, удачные вердикты возьмутся из кэша |
| Строка в лидерборде есть, деталей нет | Обновить страницу и выбрать прогон заново |
| LinksOK низкий при верных ответах | В эталоне нет источника или ссылки RAG в другом формате — проверить поле «Источник» |

## 10. Для администратора: судьи

- Модель: переменная `EVAL_MODEL` сервиса (сейчас `deepseek/deepseek-v4.1-flash` через OpenRouter).
- Промпт и логика: `src/submission/submit.py` (`SYSTEM_PROMPT`).
- После смены промпта **или модели** увеличить `_PROMPT_VERSION` там же — иначе старые вердикты возьмутся из кэша.
- Старые прогоны при смене судьи не пересчитываются — их надо перезалить.
